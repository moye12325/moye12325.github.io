用 MCP 按需投喂指令：23 条规则下的遵循率对比 ⭐️ 6.0/10

作者发布 jitprompt：把业务规则文档集中存放，通过 MCP 让 agent 根据自己的计划检索，只返回相关片段，而不是把全部内容塞进系统提示或走常规 RAG。在其基于 τ²-bench 银行知识库的测试中，向约 300K tokens 注入 23 条业务规则，使用 Claude Haiku 5.5、每任务 2 次试验，规则遵循率为 jitprompt 85%、BM25 RAG 67%、全量提示 50%；每对话成本为 $0.0086 对 $0.148。作者称优势集中在跨文档例外、新旧政策替换和“先检查再执行”流程，但承认只覆盖一个模型家族、23 条规则、自建 harness，且 RAG 基线仅为 BM25，完整方法需查看公开仓库与博客。

rss · r/PromptEngineering · 10月21日 14:32

「怎么用」 若手头有大量政策或操作规则，可先用其免费层上传现有文档，观察 agent 是否按计划读取目录并只取相关章节；再在自己的任务集上对照全量提示与 RAG，重点测例外规则和步骤顺序。材料未给出接入细节、延迟数据和失败案例，正式采用前需检查公开 harness，并补做成本与延迟评估。

「为什么值得注意」 当 agent 承担真实运营流程时，长系统提示导致的遵循衰减是实际痛点；这篇发布帖提供了一个可试用的 MCP 方案和公开评测入口，但效果仍属作者自测，尚不能视为独立验证的结论。

DuckDB 2.0.0 LTS 发布，社区聚焦客户端-服务器与触发器 ⭐️ 9.0/10

DuckDB 发布 2.0.0 LTS 版本，代号 Cinnamon Teal，面向需要长期稳定运行的分析型部署。根据社区讨论，这一版本引入客户端-服务器架构和触发器：前者让 DuckDB 可作为集中式分析服务使用，后者被用户视为补齐数据仓库能力的一步。由于没有版本说明正文，具体兼容性、支持周期和迁移要求尚不清楚。

hackernews · nnx · 10月21日 14:01 · 社区讨论

「背景」 DuckDB 此前主要以进程内嵌入式分析数据库的形态被使用：它作为库被链接进应用或数据工具，而不是以独立服务器方式部署。此次 2.0.0 版本带有 LTS（长期支持）标识，社区评论把新增的客户端-服务器部署能力和触发器（Triggers）视为相较以往嵌入式用法的关键变化。

「对部署方式的影响」 对于打算把 DuckDB 2.0.0 LTS 当作集中式分析服务运行的用户，最直接的兼容性问题是接入协议：有评论者报告称，Quack 协议的客户端支持目前仍然有限，实际部署往往需要借助 Postgres wire protocol 或 Arrow Flight（ADBC）扩展，才能让现有数据工具连上。因此，在把依赖嵌入方式的分析流程迁到客户端-服务器模式前，应先确认所用工具支持哪种协议，而不是假定它能直接对接。

「社区讨论」 有评论者报告已在生产环境运行 alpha 版，将 DuckDB 作为小型组织的集中式分析服务器，并自行开发扩展以通过 Postgres 线协议或 Arrow Flight 连接；他同时指出 DuckDB 自有的 Quack 协议客户端支持仍很有限。另有评论认为客户端-服务器模式会替代许多现有数据栈，触发器则让 DuckDB 更接近“开箱即用的数据仓库”，但这些属于个人判断而非已验证的基准结果。

LiteLLM 1.107.0 的 PyPI 包被指植入凭据窃取器与后门 ⭐️ 8.0/10

据 SafeDep 的报告，PyPI 上的 LiteLLM 1.107.0 发布包被指遭到供应链入侵，据称安装后会植入凭据窃取程序和后门。使用该版本或自动拉取该依赖的 AI 工程团队应立即审计依赖锁定文件和构建产物，并轮换可能暴露的凭据。现有材料尚未说明攻击者身份、具体受影响范围或已修复版本，相关结论仍需以进一步披露为准。

hackernews · abhisek · 10月21日 14:00 · 社区讨论

「背景」 LiteLLM 是一个通过 PyPI 分发的 Python 包；其 1.107.0 版本的 wheel 被发现带有 .pth 凭据窃取器和 sitecustomize.py 后门，这两类文件可以在每次 Python 启动时自动执行。对发布产物的核查还显示，该版本全部 7 个 wheel 都受影响，但 v1.107.0 的 git 标签中没有这些载荷，恶意代码是在构建 wheel 之前被注入构建树的。

「实际影响」 任何安装过 LiteLLM 1.107.0 的 Python 环境（全部七个 wheel 及相关 Docker 镜像）都应视为已失陷：恶意代码会在任意 Python 进程启动时执行，即使该进程从未导入 litellm，并会窃取云凭据、私钥、浏览器数据和 AI 开发工具认证文件。开发和运维团队应立即隔离受影响主机、轮换相关凭据，并将依赖固定到 1.107.0 之前的版本，待上游完成清理与验证后再升级。

「社区讨论」 评论者称这已是 LiteLLM 在一两年内第二次重大供应链事件，并提到攻击者获取了三个开发者的 GitHub 凭据，认为问题可能具有系统性，建议在进一步通知前固定使用更早版本。另一位评论者则认为，沙箱规则和频繁的权限弹窗难以阻止这类攻击，开发者对安装依赖和授予权限已逐渐麻木。

PHP 8.2.35 已发布，相关讨论称这是一次 PHP 安全发布，但发布标签本身没有提供补丁说明或技术细节。Hacker News 评论将其与名为 PHP2Shell 的 PHP 远程代码执行漏洞协同披露联系起来，并援引 Wiz、Calif 和 OpenAI 的页面；这些链接在讨论时尚未上线，因此漏洞机制、影响版本和利用条件仍未确认。还有评论提到可能存在第二个漏洞，但同样没有已发布的技术细节。对于仍使用 PHP 8.2 分支的部署者，当前公开信息主要是版本号与社区指向的严重安全问题，而非具体修复内容。

hackernews · tuyuri · 10月21日 13:45 · 社区讨论

「事件前情」 PHP 8.2.35 属于 PHP 2 Shell 漏洞的紧急修复版本之一；该漏洞是一组允许远程代码执行的安全缺陷，编号为 CVE-2026-109618 与 CVE-2026-109619（据维基百科条目）。据 Wiz 博客，Wiz Research 于 2026 年 8 月 19 日借助 AI 工具发现首个漏洞，并与 PHP、OpenAI、Calif 协调披露；漏洞存在性于 10 月 20 日公开。The Hacker News 报道称，PHP 团队同时在 8.5.12、8.4.27、8.3.36 和 8.2.35 中提供修复，并强调只有升级才能完全保护服务器。

「社区讨论」 有评论者称自己二十年来托管 PHP 从未因漏洞预先下线服务器，并批评此次披露与发布流程的处理；另一名评论者记录了 8.4.27 标签虽已出现、却仍缺少 amd64 镜像的延迟。这些是个人经验和判断，不等同于对漏洞严重性或修复状态的独立确认。

eMudhra CA 弱密钥被曝毫秒级破解 ⭐️ 8.0/10

安全研究者 Scott Helme 的文章称，受信任的证书颁发机构 eMudhra 的 CA 密钥因强度不足，可在毫秒级被破解，构成 PKI 信任问题。原始报告者 Wayne 在评论中称，发现过程直接使用了 Google 的 paranoid_crypto，对 CCADB 证书语料做初筛，随后更全面地检查现有 CCADB 证书，未再发现其他命中。文章讨论的修复重点是更新各平台的 CA 证书包，以及处理无法更新的设备。

hackernews · hkc · 10月21日 09:08 · 社区讨论

「背景」 证书颁发机构（CA）用私钥为签发的证书签名，而浏览器和操作系统通过内置信任库把特定的根 CA 和中间 CA 视为可信；一旦中间 CA 的私钥泄露，攻击者就可能伪造出被这些信任库接受的证书。在本次报道前，Mozilla 与 Chrome Root Program 已于 10 月 20 日确认 eMudhra 的 8 个中间 CA 证书私钥遭到泄露，本次事件正是围绕这些可被快速破解的弱密钥及其信任链影响展开。

「影响与处置」 对系统管理员和开发者而言，实际动作是更新操作系统 ca-certificates、certifi、Node、Homebrew 等 CA 包，并重建容器镜像；无法打补丁的 IoT 或嵌入式设备无法用同样方式修复，仍是长期暴露面。

「社区讨论」 评论区中，jlmorton 认为“有 100 个受信任 CA 可能本来就过多”，这是对 CA 生态的批评而非事件结论；jasonjayr 则强调真正困难的是无法更新或难以更新的设备。另有评论者询问能否用这些坏密钥生成看似有效的证书来越狱设备，并声称已在发生，但该说法未获独立证实。
