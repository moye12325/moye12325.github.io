从 Python 高频回调到原生求解，以及单进程多核计算的实现与验证。

在实验分析中，一份曲线可能只有几十个采样点，拟合却需要运行很久。增加工作线程后，任务看起来同时开始，CPU 仍然只忙一个核心。这类问题很容易被归结为“Python 慢”或“线程受 GIL 限制”，但这两个判断还不足以指导改造：慢的是模型公式、数组操作、求解器，还是它们之间的调用？应该编译哪一段，释放 GIL 又能改变什么？

本文以一次腔扫频分析的优化为例，解释我们怎样定位高频调用、编译模型与残差、接入原生求解器，并验证数值结果。研究使用历史真实实验数据，重点是**保持既有计算行为的前提下，减少每次求值的执行成本，再让独立拟合能够在同一进程内并行**。

原型在选定的 7 个比特、224 个任务上完成了数值与图片核对。完整分析三轮耗时中位数由 171.754 秒降至 82.415 秒；单独重放这批拟合输入，原生实现由 1 线程的 4.716 秒降至 20 线程的 0.435 秒。**完整计时存在后台活动，两项结果的测量范围也不同**，后文分别说明；当前实现仍是针对特定模型和求解条件的研究原型。

## 1. 从实验数据到拟合结果

腔扫频实验在一组频率上测量响应，得到频率数组 `x` 和响应数组 `y`。在功率扫描实验中，不同功率分别产生一条曲线；各条曲线分析完成后，父分析再根据本次子结果及其质量进行汇总。

我们详细研究的子曲线包含 61 个采样点。最初的单比特样本编号为 q1，包含 31 个子任务与 1 个父任务，共 32 个任务。单条曲线的分析过程是：

```text
读取实验数据
  → 整理频率和响应数组
  → 估计模型初值
  → 求解拟合参数
  → 判断质量并提取实验结果
  → 绘图和保存
```

模型采用六参数的偏斜洛伦兹函数，参数为 `A1、A2、A3、A4、fr、Ql`。其中 `fr` 描述模型中的频率位置，`Ql` 与曲线宽度有关，其他参数描述背景、幅度和偏斜。模型在代码中的表达式如下：

```python
def model(x, A1, A2, A3, A4, fr, Ql):
    return (
        A1 + A2 * (x - fr)
        + (A3 + A4 * (x - fr))
        / (1.0 + 4.0 * Ql**2 * ((x - fr) / fr)**2)
    )
```

一次模型求值，是给定一组参数，算出 61 个位置上的预测响应。残差函数再计算“预测响应减实测响应”，得到误差数组。求解器根据误差调整参数，直到满足停止条件或达到求值上限。所用的是无有限边界的 Levenberg–Marquardt 求解路径。

这里要区分**求值次数与求解迭代次数**。求解器可能为了估计数值导数，在一次迭代中尝试多组参数，因此一次拟合会多次调用模型。测试中一条较容易的曲线记录了 85 次求值，而一批困难输入累计约有 58 万次模型求值。

EPD 是保存实验数据及元信息的二进制文件。本文离线读取这些文件，并调用原实验分析类；不包含仪器采集、实验编译和网络传输。完整分析保留父子输入重建、质量判断、绘图和本地保存，纯拟合试验则从真实分析中捕获求解输入后单独重放。

## 2. 小数组背后的高频调用

最初的实现通过 SciPy `curve_fit` 求解：

```python
parameters, covariance = curve_fit(model, x, y, p0=initial, ...)
```

这行代码下面并非只有模型计算。**SciPy 的 MINPACK 求解器原本就已经是编译后的 Fortran 程序，但它需要反复调用 Python 函数来获得误差。** 而 Python 函数中还包含模型包装、数组转换和检查。

### 2.1 残差包装

模型返回预测值，求解器需要残差。SciPy 为模型创建了一层包装，本次无加权路径的核心是：

```python
def func_wrapped(params):
    return func(xdata, *params) - ydata
```

这层函数固定住实验输入 `xdata` 和 `ydata`，把求解器给出的参数传给模型，并将预测值与实测值相减。每次求值都会经过这层 Python 函数。

### 2.2 模型类型包装

原分析库还给模型添加了类型转换装饰器。下面保留了其主要逻辑：

```python
def wrapper(x, *args, **kwargs):
    values = model_body(x, *args, **kwargs)
    try:
        if isinstance(x, float):
            return float(values)
        return values.astype(float)
    except TypeError:
        return values
```

装饰器用于处理模型可能返回的不同数值类型。对本次输入，`x` 是数组，通常执行 `astype(float)`。**NumPy 的 `astype` 默认要求复制，即使数据已经是目标类型，这种写法通常仍创建新数组。**

61 个双精度数的数据量仅约 488 字节，但一次转换还包含数组对象创建、分配和复制等工作。单次成本不大，几十万次重复就会累积。适配明确的输入类型后，可以减少这部分通用处理；这不意味着可以在其他调用条件下直接删除装饰器。

### 2.3 参数缓存检查

本次 SciPy 版本还在残差外增加浅缓存，保存第一次参数及结果，以避免初始化时的重复计算。后续调用会经过类似的判断：

```python
if np.all(saved_params == params):
    return saved_result
```

这不是缓存全部历史求解结果。对大多数新参数，程序仍然要计算残差，但先承担一次参数比较和归约判断的成本。

输入形状、有限值等准备检查主要在拟合开始时执行，与反复求值时的缓存判断不同。**优化需要区分一次性准备和高频内部调用，不能把所有检查都视为每次求值的成本。**

### 2.4 模型表达式的执行

模型中的加减乘除大量使用 NumPy，它们的底层运算本来就是编译代码。但原函数仍由 Python 组织各个操作：传入数组、取得结果，再发起下一项操作，其中可能产生临时数组。

对大型数组，一次底层运算持续较久，调用成本往往能够被计算量摊薄。61 点数组的单次计算很短，函数分派、数组分配和对象管理就更容易成为明显开销。因此，已经使用 NumPy，并不代表高频小数组模型没有进一步编译的价值。

## 3. 性能证据与线程表现

我们先进行阶段计时，确认拟合在完整分析中的累计成本，再捕获真实求解输入，单独比较线程。每份输入保留模型、数组、初值、容差和求值上限，避免用人工生成的简单曲线代替困难任务。

工具按问题选择。cProfile 用于早期调用关系与热点分析；转向多线程问题后，增加 Yappi，分别观察线程 CPU 时间和经过时间；py-spy 则从外部采样调用栈及持有 GIL 的栈。

| 工具 | 主要观察 |
|---|---|
| 阶段计时 | 拟合与其他阶段的累计时间 |
| cProfile | 函数关系与高频调用 |
| Yappi | 各线程的 CPU 与经过时间 |
| py-spy | 运行中的调用栈样本 |

Yappi 适合后续研究，是因为它直接支持多线程统计和 CPU/wall 时钟选择。**它补充了 cProfile，而不是证明 cProfile 不适用或不可靠。** 函数剖析会增加成本，最终速度比较使用关闭剖析器的正常运行。

一轮独立 CPU 剖析中，模型表达式出现约 581,208 次，`astype`、参数缓存、残差和数组归约也出现了相近数量的调用。这说明相邻包装层随每次模型求值反复执行。py-spy 的有效拟合 GIL 样本中，约 59.2% 的最内层 Python 帧落在模型表达式，为定位提供了另一份证据。

这些统计有边界：采样比例不等于完整运行耗时比例；多个线程的经过时间可以重叠；Yappi 的 CPU 与 wall 分别来自不同运行，不能相减为精确 GIL 等待时间。我们用它们定位执行位置，再用受控试验检验原因。

原实现增加到 8 个工作线程后，一组正常试验的中位时间从 16.649 秒变成 18.071 秒，平均仍约使用一个逻辑核心。这里每个线程处理独立拟合，数值库内部线程上限固定为 1。线程已经启动，并不表示几个核心同时在计算。

当前 CPython 的 GIL 限制同一进程内 Python 代码的并行执行。部分 NumPy 操作能够释放 GIL，但本次单次运算很短，随后很快返回 Python 包装。结合相应版本求解入口的源码与运行观察，这条调用链没有形成足够长的并行计算阶段。**这个判断针对单进程多线程，不意味着多进程也受同一把 GIL 限制。**

## 4. 第一步：编译模型

首先保留原公式，取出类型包装内的模型函数体，用 Numba 编译。Numba 的 `njit` 根据输入类型，将支持的 Python 数值函数转换为机器代码。

下面是编译入口的简化示意；实际版本还包含后文介绍的标量幂兼容处理：

```python
body = wrapped_model.__wrapped__
compiled_model = njit(fastmath=False)(body)

# Compile and warm up before normal timing.
compiled_model(x, *initial)
```

`__wrapped__` 指向装饰器内部的公式函数，因此编译路径不会再进入外层类型包装。输入类型明确后，也无需在每次求值结束时重复执行原来的通用 `astype`。

第一次遇到相应输入类型时生成机器代码，后续参数变化直接复用。参数数值改变不会要求每次重新编译；遇到新的输入类型可能生成另一份专门版本。

**只编译模型，仍没有消除求解循环中的 Python 残差回调。** 这一阶段的调用关系变成：

```text
SciPy 求解器
  → Python 参数缓存与残差包装
  → 编译后的模型
  → 返回残差
```

在修正数值差异后的一组正常三轮对照中，保留 GIL 的单线程拟合由 16.009 秒降到 5.451 秒，耗时减少约 66.0%。这部分改善来自模型编译及省去相应包装，两者贡献没有被单独量化。**由于该版本仍保留 GIL，不能把 66% 归给释放 GIL。**

尝试仅在单次模型调用期间释放 GIL，并没有使真实拟合随线程数增加而变快。释放的计算片段太短，外面的 Python 回调仍在，额外的锁切换还可能增加成本。编译一个函数与使整个拟合并行，是两个不同层次的问题。

## 5. 第二步：连接原生求解

模型加快后，内部高频 Python 回调成为进一步优化的对象。我们希望 Python 在拟合开始时交入数据，求解器直接调用编译后的残差和模型，整次求解完成后再返回 Python。

![三种拟合调用方式](/images/curve-fitting-native/01-fit-calls.png)

图 1：浅蓝是 Python 执行部分，深蓝是编译代码。中间调用随求值重复，图中宽度不代表时间。第三条路径将反复迭代连接在原生代码内。

在所用 SciPy 1.11.4 中，`curve_fit` 没有直接接受原生残差函数指针的接口，本机扩展也没有直接导出所需求解入口。因此原型引入 CMinpack 的 C 接口。它实现同类 MINPACK 求解算法，能够接收符合 C 调用约定的残差函数。

这一选择同时改变了求解器的编译实现。后续性能差额包含调用链及实现变化，不能把全部时间差严格归给某一个 Python 包装函数。数值兼容问题也必须重新验证。

### 5.1 三种编译产物

模型仍由 Numba `njit` 编译。残差则用 Numba `cfunc` 编译为可按 C 调用约定进入的函数；它提供函数地址，供求解器直接调用。求解器 C 源码通过 Visual Studio 编译成 Windows 动态链接库。

| 部件 | 编译方式 | 当前产物 |
|---|---|---|
| 模型 | Numba `njit` | 进程内存中的机器代码 |
| 残差 | Numba `cfunc` | 机器代码及 C 函数入口 |
| 求解器 | C 编译器 | `cminpack.dll` |

**模型和残差没有被打包进求解器 DLL。** 当前实现运行时编译它们，再把残差函数地址传给 DLL。模型编译对象和残差回调对象需要在调用期间保持存活，不能只留下一个已经失效的地址。

### 5.2 输入内存与残差计算

每份拟合开始时，Python 准备 `float64` 输入和独立工作数组，把数据内存地址、六个初值、容差、求值上限及残差函数地址交给求解器。

编译后的残差从内存中取得频率、实测值和本次参数，调用模型，再将差值写入求解器提供的输出数组。下面只表示计算关系，省略 C 函数签名与地址处理：

```python
# Schematic body inside the compiled callback.
predicted = compiled_model(x, *parameters)
for i in range(point_count):
    residual_output[i] = predicted[i] - measured[i]
```

这里没有进程间传输，也没有每次求值重新读取文件。输入准备和部分复制仍在每份拟合开始时发生；编译后的模型也不保证没有任何临时分配。减少的是循环内部反复经过 Python 的成本，不能称为整个过程完全零复制或零分配。

### 5.3 保留 Python 外层

原型没有将整套实验分析改写为 C。Python 继续负责数据读取、输入条件判断、结果处理、质量判断、父子汇总、绘图和保存，SciPy 外层的协方差与错误处理也继续使用。

为了接入既有流程，研究代码临时替换 SciPy 私有的 `_minpack._lmdif` 入口，将符合条件的调用交给原生适配器；不支持的调用交回原实现，结束后恢复入口。这种替换适合受控研究，依赖具体版本，正式服务需要明确的后端接口，不能把全局临时替换直接作为长期并发设计。

## 6. GIL 与同进程并行

Python 使用 `ctypes.CDLL` 调用 DLL 时，会在原生调用期间释放 GIL。求解器内部再直接调用编译后的残差和模型，不需要每次回到 Python 执行函数。线程 A 处理一份拟合时，线程 B 因而可以处理另一份独立拟合。

实际原型中，模型仍以 `nogil=False` 编译，这与外层释放 GIL 不矛盾：该选项控制从 Python 调用模型时的释放行为；这里求解器经 C 回调直接进入编译模型，由外层 DLL 调用释放 GIL。正常计算路径不需要在每次模型求值时重新进出 Python。

释放 GIL 并不会自动启动工作线程，也不会让一份求解自动拆成多个核心。本次并行单位是**多份相互独立的拟合**。线程池负责分配这些任务，父分析仍要等待所需子结果；尚未到达的数据也不能提前计算。

我们用同一个 DLL 做持有与释放 GIL 的对照：`ctypes.PyDLL` 保留 GIL，`ctypes.CDLL` 释放 GIL。每份任务使用独立工作数组，避免共用可变求解状态。

| 原生调用方式 | 工作线程 | q1 中位时间 / 秒 |
|---|---:|---:|
| 持有 GIL | 1 | 0.649 |
| 持有 GIL | 8 | 0.657 |
| 释放 GIL | 1 | 0.657 |
| 释放 GIL | 8 | 0.139 |

单线程下两种方式接近；持有 GIL 时增加线程基本没有收益，释放后才出现并行改善。这组对照把两项收益分开了：**减少 Python 往返改善单线程，释放 GIL 使多份拟合能够同时计算。**

## 7. 浮点一致性的三次排查

性能更快还不够。拟合反复依据很小的数值变化调整参数，公式相同也不保证不同编译实现得到相同轨迹。我们没有放宽容差来接受变化，而是追查差异并重新验证。

### 7.1 标量幂与连乘

普通模型编译初版出现过 6 次拟合差异。沿原求解轨迹逐次比较模型输出时，定位到 Windows 下标量 `Ql**2` 的计算差别：

```text
Ql = 511667.9232423212
原标量幂结果：261804063675.1099
编译连乘结果：261804063675.10986
```

模型输出的差别可小至约 `2.78e-17`，最终参数差异却可能明显放大。仅关闭 `fastmath` 没有解决已知问题。

修正通过自定义 Numba 编译步骤，让对应浮点标量幂调用 Windows 运行时 `pow`，保留原函数体和所需运算行为。检查 8 条真实轨迹、270,265 次模型求值时，普通编译版本有 71 处不同，修正后未发现差异。这个处理依赖当前平台与模型，不能直接当作所有 Numba 函数的通用补丁。

### 7.2 求解器机器常数

接入原生求解后，发现 SciPy 与 CMinpack 的机器精度常数略有不同，分别为 `2.22044604926e-16` 和 `2.220446049250313e-16`。

求解器用机器精度确定数值求导时的参数试探步长，微小差异也可能改变后续轨迹。匹配当前 SciPy 的三个 `dpmpar` 常数后，最初单比特的差异消失。

### 7.3 向量长度计算阈值

扩大到 7 个比特后又发现两类差异：一份输入的 `Ql` 相差约 7.72%，另一份仅协方差末位不同，图片却相同。这说明单比特通过并不足够，像素相同也不能替代数值检查。

对照“编译模型＋SciPy”“原生持有 GIL”“原生释放 GIL”后，前者一致，两个原生版本出现相同差异，问题因此指向求解实现，而非线程竞争。

最终定位到计算向量长度的 `enorm`。它为避免平方溢出或下溢，按数值大小分组处理；两个实现的分组阈值不同：

| 阈值 | 当前 SciPy | 原 CMinpack |
|---|---|---|
| 小值 | `3.834e-20` | `1.82691291192569e-153` |
| 大值 | `1.304e19` | `1.34078079299426e153` |

分组差别会改变运算路径和累加顺序。在保留前两项兼容处理的基础上，匹配这两个阈值、使用严格浮点编译设置后，已知差异消失，再重新执行全部核对。

**这些修改的目标是匹配当前 SciPy 的行为，不能据此判断原 CMinpack 的数学实现有误。** 当前样本逐位一致，也不等于对所有输入已经证明等价。换平台、编译器、依赖或求解条件后，仍需重新验证。

## 8. 分层性能结果

测量机器为 Xeon W-2255，10 个物理核心、20 个逻辑处理器，约 256 GiB 内存，运行 Windows Server 2022。主要环境是 Python 3.12.13、NumPy 1.26.4、SciPy 1.11.4、Numba 0.61.2 与 llvmlite 0.44.0。

正常计时与函数剖析分开。以下主要性能对照在计时前完成模型编译、预热和线程池启动，不包含首次编译成本。数值库内部线程固定为 1，避免与拟合工作线程形成多层线程竞争。

### 8.1 单比特调用方式对照

下表来自同一组 32 次捕获拟合，取正常三轮中位数，不包含 EPD 读取、绘图和保存。该组使用最初单比特验证的 DLL，后续扩大验证又增加了向量长度阈值兼容处理，因此不与后续秒数拼成同一组试验。

| 执行方式 | 工作线程 | 中位时间 / 秒 |
|---|---:|---:|
| 原模型＋SciPy | 1 | 13.590 |
| 编译模型＋SciPy | 1 | 4.933 |
| 编译模型＋SciPy | 8 | 5.271 |
| 原生求解释放 GIL | 1 | 0.657 |
| 原生求解释放 GIL | 8 | 0.139 |

![不同调用方式的拟合时间](/images/curve-fitting-native/02-q1-comparison.png)

图 2：横轴为秒数，从零开始。前几组比较实现变化；最后两组才比较同一原生实现的线程收益。0.657→0.139 秒约为 4.74 倍，不能将 13.590→0.139 解释成单靠增加线程获得约 98 倍提升。

原生调用减少了内部 Python 往返，但也更换了求解器编译实现。实验没有把模型编译、包装减少和求解器实现各自贡献完全拆开，因此这些因素应共同解释单线程改善。

### 8.2 扩大后的线程能力

使用修正后的原生版本，对 7 个比特捕获的 224 次调用重放，各配置三轮。输入已在内存，计时包含任务提交、原生求解、Python 参数检查和协方差计算，不包含文件读取、图片、编译及结果核对。

| 工作线程 | 中位时间 / 秒 | 平均逻辑核心 | 相对 1 线程 |
|---:|---:|---:|---:|
| 1 | 4.716 | 0.99 | 1.00 倍 |
| 2 | 2.347 | 1.98 | 2.01 倍 |
| 4 | 1.355 | 3.85 | 3.48 倍 |
| 8 | 0.797 | 7.51 | 5.92 倍 |
| 10 | 0.684 | 9.21 | 6.89 倍 |
| 20 | 0.435 | 15.46 | 10.84 倍 |

![线程数量与拟合性能](/images/curve-fitting-native/03-fit-threads.png)

图 3：仅拟合的线程对照。平均核心数由工作线程 CPU 时间合计除以整批经过时间计算；它是并发计算量的估计，不代表相同数量的物理核心。20 线程平均约用 15.46 个逻辑核心，说明单进程已经能够多核计算。

任务长短不均，部分线程会在其他线程完成前先空闲。操作系统调度、线程管理和超线程也影响收益，线程数量与加速比不会始终成正比。20 线程在当前样本最快，尚不足以作为所有服务请求的固定配置。

> 短配置试验只在整次开始前观察背景负载，没有逐配置持续采样。它证明当前样本具有同进程并行能力；稳定吞吐仍需要在可控制的环境和持续输入下测量。

### 8.3 完整分析的效果

最后将原生拟合接回完整分析，保留读取、质量判断、父子汇总、图片与本地保存。224 个任务仍顺序执行，完整流程没有采用上面的并行拟合。

| 指标 | 原流程 | 原生版本 |
|---|---:|---:|
| 整批中位时间 | 171.754 秒 | 82.415 秒 |
| 拟合中位时间 | 95.154 秒 | 4.695 秒 |

完整时间约减少 52.0%，主要来自单线程内部拟合执行的改善。图像渲染保存仍约 60.7 秒，新流程中拟合只占约 5.7%。因此不能用纯拟合约 10.84 倍的线程加速，推断整个分析也能再快同样倍数。

![完整分析的阶段组成](/images/curve-fitting-native/04-complete-stages.png)

图 4：两侧分别选择总时间处于中间的实际轮次，各段属于同一轮，可以相加。它不是把各阶段分别取中位数后拼成的一次运行。

> 两种完整实现各运行三轮，六轮均有超过预设阈值的后台活动，符合低负载条件的配对为 0。52.0% 仅描述本机当时的三轮结果，不能作为专用服务器的稳定性能承诺。单独资源观察轮也显示完整链仍约使用一个核心，没有证明整个服务已经用满整机。

## 9. 结果一致性验证

为了避免“更快但结果不同”，验证分两层进行。第一层捕获原拟合的数组、初值、选项和输出，检查参数、协方差、残差、异常与求值次数；第二层重新执行完整父子分析，检查质量、父输入、保存错误、输出文件和图片。

扩大验证包含 217 个子拟合和 7 个父调用。原生路径处理 217 个子拟合，父模型保留原实现。194 次调用正常返回，23 次子拟合达到最大求值次数，7 次父拟合因空输入失败。异常路径也参与对比，没有为了速度丢弃困难输入。

| 检查项 | 数量 | 修正后结果 |
|---|---:|---|
| 输入 x、y、p0 | 各 224 份 | 原始字节一致 |
| 参数、协方差、残差 | 各 194 份 | 原始字节一致 |
| 返回、异常、求值次数 | 224 次 | 一致 |
| 输出文件 | 896 个 | 哈希一致 |
| 图片 | 224 张 | RGBA 像素一致 |
| 父输入 | 7 组 | 使用本次子结果 |

**数值求解正常返回，不等于实验质量通过。** 这批任务的完整分析质量均为 `not_pass`，两侧保存错误均为 6。因此当前结论是保持原流程已有的数值、质量与异常行为，没有证明实验质量改善，也没有覆盖正常父拟合。

参数一致而协方差不同，可能影响后续不确定度判断；图片相同也可能掩盖这种变化。所以检查不能只比较最终频率或图片。逐像素比较用于发现展示变化，出现差异时另生成前后与差异合成图，供人工审核。

严格字节一致适合这次需要复现既有行为的改造。其他项目可以依据科学要求制定数值容差，但应在优化前明确，不能在出现未知差异后临时放宽标准来接受实现。

## 10. 适用条件与工程取舍

这条路线适合高频调用小模型、Python 包装成本明显，并且存在多份独立拟合的场景。它不要求实验使用相同公式，但每个新模型都要确认能够编译、输入类型明确、求解方式兼容，并重新验证数值行为。

如果主要成本是一次大矩阵运算、文件等待或图片布局，编译本次模型未必有同样价值。若只有一份拟合可做，释放 GIL 也不会凭空增加独立任务。数据到达较慢或父任务等待子结果时，CPU 空闲需要结合任务依赖解释。

当前原型支持本次六参数模型、无加权 `sigma`、无自定义 `jac`、`lm` 和无有限边界等条件，不支持的调用保留原路径。其他模型、加权或边界求解、正常父拟合都尚未完成验证。

部署时还需要处理几个具体问题：

- 为模型、残差、DLL 和数值库保存版本及编译信息，变更后重做正确性检查。
- 服务启动时编译预热，并单独测量启动成本，避免首次请求承担未说明的延迟。
- 保持回调对象有效，为每份拟合分配独立状态，限制工作线程数量。
- 对求解失败、回调失败和不支持条件明确返回错误或转用原实现。
- 持续观察完成速度、等待时间和内存增长，不能只追求 CPU 占用数字。

其中私有接口替换、Windows 标量幂兼容和 CMinpack 常数匹配，都属于当前原型的版本依赖。正式服务应把模型、求解后端及支持条件显式组织起来，在请求进入时决定执行路径，避免其他线程受到临时全局替换影响。

## 11. 对分析服务的启示

这次优化提供了两种已经分开验证的能力：单份拟合减少 Python 调用成本，多份独立拟合利用释放 GIL 的原生调用并行计算。两者组合后，单进程不再只能依赖一个核心，但完整分析仍然受到其他阶段影响。

后续工作应把已验证的拟合能力接入完整任务组织，同时研究布局复用，以及数值结果先返回、图片稍后完成的流程。后者改善调用方等待时间，图片计算仍然存在，需要限制积压并测量全部产物的完成时间。

性能判断最终要回到有效产出：相同结果下，每秒完成多少分析，调用方多久得到结果，长时间运行是否稳定。CPU 在有任务时用于有效计算，内存用于支持必要的并发和复用。**占用更高只有在带来更多有效产出时才有意义。**
