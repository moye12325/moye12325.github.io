### [Check Point 管理服务器遭活跃入侵，PRNG 状态恢复可伪造管理员会话](https://www.greynoise.io/blog/check-point-security-management-servers-intrusion-campaign) ⭐️ 8.0/10

Check Point 安全管理服务器正遭遇一场活跃入侵活动，报道称攻击链包含利用 JavaScript PRNG 状态恢复来伪造管理员会话 Cookie。评论中引用的分析称，攻击者向 HFS 的 loginSrp1 端点连续发送 POST，收集由 Math.random() 生成的 sid，重建 Node.js V8 PRNG 状态，进而恢复 HFS 会话 Cookie 签名密钥并伪造管理员 Cookie。公开讨论尚未确认初始访问方式；有评论推测与 CVE-2026-16232 以及管理服务器暴露在互联网上有关，但这仍是推测。

hackernews · louiereederson · 11月24日 16:32 · [社区讨论](https://news.ycombinator.com/item?id=50630594)

**「背景」** Check Point 早在 7 月就披露并修复了 CVE-2026-16232：这是 SmartConsole 登录流程中的认证绕过漏洞，未认证的远程攻击者可借此取得应用登录令牌，并以完整管理员权限通过认证（NVD 记录的披露日期为 7 月 22 日）；官方公告补充说明，远程利用的前提是管理服务器的 IP 地址可经互联网访问，且未对 Trusted Clients（GUI 客户端）设限，9 月的更新中仍给出这一条件。就本次入侵而言，另一个前提概念在于 JavaScript 的 Math.random() 不具备密码学安全性：HFS 登录接口返回的会话 cookie 中，sid 由 Math.random() 生成；攻击者通过连续登录收集足够输出，便可重建 Node.js V8 中 PRNG 的内部状态，从而恢复 cookie 签名密钥并伪造管理员会话。

**「影响」** 对运行 HFS 的 Check Point 管理服务器而言，关键后果是攻击者可能绕过正常登录伪造管理员会话；运营方应检查 HFS 是否暴露于互联网、审计异常登录并轮换会话签名密钥。

**「社区讨论」** 评论中最实质的争论是根因应归咎于 Math.random() 本身还是误用它的应用：有评论认为应让随机数生成器默认更安全。另一些评论追问初始访问途径，认为多家 Check Point 客户中招可能意味着管理服务器暴露在互联网上，但这一点尚未确认。

### [开源 Mason：基于 DuckDB 的 PostgreSQL 只读副本](https://masondata.ai/) ⭐️ 7.0/10

Mason 是一个开源、可直接替换 PostgreSQL 只读副本的工具，底层使用 DuckDB 的列式存储与计算引擎，目标是让分析型查询在不改写 SQL 的情况下运行。作者自测称，在来自 159 个真实 PostgreSQL 数据库的 5,410 条手写慢查询中，Mason 有 96% 返回与 PostgreSQL 完全一致的结果，其余 4% 会报错并提示如何改写；他们还补充了数百条查询，并用 Metabase、Grafana、Superset、DBeaver 和 Trevor.io 做了兼容性测试。这些正确性数字来自作者自己的基准，并非独立测量；“非常快”的性能主张也尚未给出可核验的延迟或吞吐数据。

hackernews · tagspace · 11月24日 16:11 · [社区讨论](https://news.ycombinator.com/item?id=50630294)

**「背景」** 团队最初尝试把分析查询直接交给 ClickHouse，但发现其引擎调优门槛较高，且 SQL 语法与 PostgreSQL 差异很大，不适合临时的 PostgreSQL 工作负载。在对比 pg_clickhouse、cedarDB 和 DuckDB 时，同一批 5,410 条查询上 DuckDB 开箱匹配 PostgreSQL 84.1%、拒绝 14.3%、结果错误 1.6%，cedarDB 分别为 88.1%、8% 和 3.9%，pg_clickhouse 为 59.4%、39.9% 和 0.8%。Mason 选择 DuckDB，是因其开源许可证便于继续补齐 PostgreSQL SQL 兼容性的长尾。

**「影响」** 对需要在 PostgreSQL 副本上跑临时分析查询的团队，Mason 提供了一条保留 PostgreSQL 风格 SQL、同时利用列式引擎的路径；但 96% 的兼容率只覆盖作者选定的查询集，部署前仍应拿自己的查询语料验证，并为剩余 4% 准备改写或回退方案。性能是否优于现有 PostgreSQL 只读副本，还需要独立的延迟和并发测试。

**「社区讨论」** 有评论者称赞这是 ClickHouse 用户也会关注的工作；另一位评论者则质疑，除了仪表盘和团队功能，Mason 相比“DuckDB + ADBC 直连 PostgreSQL”究竟增加了什么，以及 pglite 和 Node 相关组件是否必要。后者提出的是产品差异化和组件必要性的疑问，并非已验证的结论。
